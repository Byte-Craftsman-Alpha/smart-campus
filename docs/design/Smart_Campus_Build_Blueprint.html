Smart Campus Classroom Management System

A build blueprint, not a pitch. This document reads the supplied problem statement and the architect's floor plan line by line, extracts every structural constraint the buildings actually impose, reconciles the five places where the written spec and the drawing disagree, and then derives the most efficient and most convenient way to build the working prototype — data model, conflict engine, AI layer, stack choice, DevOps pipeline and a ten-day plan.

It is written so a team can open it on day one and start committing code on day one.

The one-line architecture

One TypeScript codebase (Next.js App Router on Vercel) + one managed PostgreSQL, where the database itself — via a tstzrange exclusion constraint — makes double-booking physically impossible, and the AI is a thin natural-language front door that is never trusted with a write.

The one insight that decides the design

Of the 30 bookable rooms, only 2 (Seminar Hall IET32, 200 seats; Library, 180) can seat a 75-student section in spaced exam seating. Conflict prevention is therefore not a CRUD concern — it is a scarce-resource allocation problem, and the alternative-suggestion engine is the product.

The one constraint teams forget

IET and Deeksha Bhawan are 100 m and one staircase apart, with no lift in either building. Every recommendation must charge a time-and-effort penalty, or the system will cheerfully schedule a section into a room they cannot physically reach in time — which is the exact failure the problem statement was written about.

Section 2Structural analysis of the two buildings

This is the part most submissions skip, and it is the part that makes the software correct. Every architectural fact below becomes a rule in the code. The analysis reads the plan sheet supplied on page 2 of the problem statement.

2.1 IET — massing, circulation and what it means

IET is a rectangular, three-storey block with a single central staircase and a single entry gate on the ground floor, roughly centred on the long axis. Rooms are arranged in two parallel wings — a north row and a south row — separated by a corridor, with the stair core bisecting both rows. This "dumbbell" plan is the single most important structural fact in the whole campus, because it means:

  • One stair core serves all three floors. Floor-change traffic for 600 students per year-batch funnels through one ~2 m stair. Add a stair-egress time to every cross-floor recommendation, and expect a bottleneck at period boundaries. Software implication: never schedule two activities for the same section that require an IET floor change with a zero gap; the minimum inter-activity buffer must cover a stair climb (see §2.5).
  • No lift is drawn. The seminar hall (200 seats) and six classrooms sit on the second floor, and the four laboratories on the first. Any accessibility-sensitive use (an examination for a student with a mobility limitation, a guest lecture for external attendees) must prefer ground-floor spaces — Library in IET, LH01–LH07 in Deeksha Bhawan. Software implication: an accessibility field on every room plus an accessible_only filter flag on bookings.
  • Rooms are paired across the corridor. The north and south rooms facing each other are "adjacent pairs". Two parallel sessions that a student body must hop between (e.g. a viva panel and its waiting room) are cheapest to run in an adjacent pair. Software implication: a zone field enabling an "adjacency bonus" in the ranking function.
  • The entry gate is central and single. Arrival and dispersal of a 200-person event loads one door. Software implication: for events above a headcount threshold, surface an advisory ("single entry gate; stagger entry by 10 minutes") — a small touch that reads as genuine campus awareness in a demo.

2.3 Deeksha Bhawan — a loop plan, and why it changes the algorithm

Deeksha Bhawan is not a repeat of IET. It is a seven-room bowtie per floor: two long open-plan rooms along the north side (LH01, LH02 / LH08, LH09), two compact rooms flanking the core (LH03, LH04 / LH10, LH11), one room on the east (LH05 / LH12), and two rooms flanking the entry gate on the south (LH06, LH07 / LH13, LH14), with a washroom and a drinking-water point in the middle and a single stair beside the south entry.

Three consequences that a shallow model would miss:

  • The long north rooms are the only Deeksha rooms that can hold a full 75-student section. LH01, LH02, LH08 and LH09 run the full depth of the plan; LH03/04/11/12 and LH06/07/13/14 are visibly smaller. So Deeksha cannot be treated as "14 equivalent spare rooms" — it is 4 section-capable rooms plus 10 room-suitable-for-splits. This is exactly the kind of distinction that determines whether an alternative suggestion is actually usable.
  • The washroom and drinking-water core sits between LH03/LH04 and LH05. Those rooms are the noisiest and most footfall-heavy in the building — a bad choice for a minor examination, a fine choice for a tutorial. Encode it as a disruption_penalty on those rooms for EXAM purpose, not as a hard rule.
  • One stair, at the south entry, for the entire first floor. LH08–LH12 are up a single stair from a single door 100 m from IET. Cross-building, cross-floor moves are the slowest possible journey on this campus (~340–410 s, see §2.5). The scheduler must treat that journey as expensive, and the UI must say so out loud when it recommends it.

4.2 The time model — get this right once and everything else gets easier

Almost every bug in a booking system is a time bug. Four decisions, made once, remove the whole class:

  1. Store instants, not wall-clock strings. Use timestamptz backed by tstzrange. The campus lives in one timezone, but IST is UTC+05:30 — an offset that breaks any code assuming whole hours. Let Postgres do the conversion and never do date arithmetic in JavaScript.
  2. Half-open intervals only: [start, end). A booking ending at 11:00 and one starting at 11:00 do not conflict. Getting this wrong produces the maddening "back-to-back bookings clash" bug, and it is a one-character fix if you decide on day one.
  3. Snap to 5 minutes on input; compare exactly on overlap. The grid gives neat UX; the interval gives correctness. Do not try to force every booking onto the period grid — extra classes and practicals start at odd times, and the statement explicitly asks for arbitrary durations.
  4. Never delete. Cancellations are status='cancelled' with a reason and an actor. The tstzrange exclusion constraint is written to apply only to status='confirmed', so a cancelled slot is immediately reusable while history stays intact.
-- The single most important line of SQL in the project.
-- Requires: CREATE EXTENSION btree_gist;
ALTER TABLE "Booking"
  ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    room_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
  ) WHERE (status IN ('CONFIRMED','PENDING_APPROVAL'));
Why this is the highest-leverage decision in the build

Application-level conflict checks are a race condition: two faculty members clicking "Book" in the same second both pass the check, and both rows are written. A judge will ask "what if two people book at once?" — and "the database refuses the second one" is a far better answer than "we use a transaction and hope". A PostgreSQL exclusion constraint makes overlapping confirmed bookings for the same room literally unrepresentable at the storage layer. It is ~10 lines of SQL, it needs btree_gist, it works on Neon/Supabase/RDS, and it removes an entire category of failure. Catch the resulting Postgres error code 23P01 and translate it into your friendly 409 with alternatives.

4.3 Status machine for a booking

Section 5Algorithms: availability, conflict, alternatives

The statement asks for "intelligent assistance" and "scheduling algorithms". Resist the urge to reach for a heavyweight optimiser. The high-value work here is a correct availability query, a scored alternative generator and a small, honest scheduling heuristic — all of which fit in a few hundred lines of pure TypeScript and are trivially unit-testable. That is both the efficient and the convenient path.

5.1 Availability search

Availability is not a boolean on a room; it is the complement of the union of occupied intervals within a window. Two equivalent implementations — pick one and don't build both:

-- Option A (recommended): anti-join over intervals. One round trip, uses the GiST index.
WITH occupied AS (
  SELECT room_id FROM "Booking"
   WHERE status IN ('CONFIRMED','PENDING_APPROVAL')
     AND tstzrange(start_at, end_at, '[)') && tstzrange($1::timestamptz, $2::timestamptz, '[)')
  UNION
  SELECT room_id FROM "RoomClosure"
   WHERE tstzrange(start_at, end_at, '[)') && tstzrange($1::timestamptz, $2::timestamptz, '[)')
  UNION
  SELECT room_id FROM "TimetableSlot"          -- official recurring classes
   WHERE day = $3 AND period && $4::int[]     -- overlap of period sets
)
SELECT r.*, f.level, b.name
  FROM "Room" r
  JOIN "Floor" f ON f.id = r.floor_id
  JOIN "Building" b ON b.id = f.building_id
 WHERE r.bookable
   AND r.capacity >= $5
   AND r.type = ANY($6::text[])               -- permitted by purpose
   AND ($7::bool IS NOT TRUE OR r.accessibility = 'step_free')
   AND r.id NOT IN (SELECT room_id FROM occupied)
 ORDER BY (b.id = 'IET') DESC, r.capacity ASC;  -- prefer IET, then the tightest fit

Three details that separate a working query from a demo query: (a) TimetableSlot must be included, or the "free" room is the one where a class is already running — the exact bug the project is meant to fix; (b) RoomClosure must be included, or maintenance days vanish; (c) ordering by "tightest fit" — capacity ASC within capacity ≥ headcount — matters because it preserves the big rooms for the big events — a bin-packing instinct that costs one line and makes the whole system feel considered.

5.4 Ranking alternatives — the scoring function

This function is the project's "intelligence", and it belongs in the deterministic code path, not in the LLM (the LLM may explain it, never compute it). Every term is normalised to 0–1 and then weighted. Start with these weights, then tune them live during the demo — having visible weights is itself a strong signal of engineering maturity.

function scoreRoom(candidate, request, context): number {
  // 1. HARD CONSTRAINTS — any failure means the room is not a candidate at all.
  if (!room.bookable) return REJECT;
  if (room.capacity < requiredCapacity(request)) return REJECT;
  if (!room.permittedUses.includes(request.purpose)) return REJECT;
  if (request.accessibleOnly && room.accessibility !== 'step_free') return REJECT;
  if (overlapsAnyBooking(candidate.interval, room.id)) return REJECT;   // re-validated here, always

  // 2. SOFT CONSTRAINTS — weighted sum, normalised to 0..100.
  const s =
      0.22 * capacityFit(room, request)
    + 0.20 * sameBuilding(room, context.anchorRoom)
    + 0.12 * sameFloor(room, context.anchorRoom)
    + 0.12 * purposeFit(room.type, request.purpose)
    + 0.10 * featureMatch(room, request.requiredFeatures)
    + 0.08 * (1 - disruptionPenalty(room, request.purpose))
    + 0.08 * (1 - Math.abs(candidate.shiftMinutes) / MAX_SHIFT)
    + 0.05 * (request.accessibleOnly ? 1 : room.accessibility === 'step_free' ? 1 : 0.7)
    + 0.03 * (1 - utilisation(room));

  return Math.round(s * 100);
}
Two honesty rules for the recommendation engine

(1) Re-validate at display time. The statement explicitly says recommendations must be "validated against actual booking records". A room that was free when the list was computed may be booked by the time the faculty member clicks. So the POST /api/bookings handler re-runs the constraint check, and the UI refreshes the list on a short stale-time. Recommendation is advisory; the exclusion constraint is authoritative.

(2) Explain every score. Return the top two or three contributing reasons as text ("adjacent room, same floor"). A number without a reason is not intelligent, it is just opaque — and judges ask "why did it pick that one?"

5.5 Timetable-aware allocation (the optional but impressive part)

When a room must be assigned to a whole section's weekly schedule, the objective is least disruption, not maximum packing: keep classes where they already are, and move as little as possible. A greedy pass with a local-search polish gets within a few percent of optimal on 32 sections × 8 periods, in milliseconds — do not import a MILP solver for this.

  1. Rank requests by difficulty (largest section first, most constrained purpose first, lab-feature requirements first) — the standard "most constrained variable" heuristic. This alone removes most dead ends.
  2. Greedy assignment with the §5.4 scorer; when a slot is full, allow the swap move: displace a lower-priority booking into another qualifying room if one exists, and count the displacement as cost.
  3. Local search polish: repeat N times — pick a conflicting pair, try the four standard repairs (move A, move B, swap A↔B, change period), keep the change if total cost falls. Cap at ~50 ms and report the cost before/after.
  4. Report the cost decomposition in the UI: "12 classes kept, 3 moved, 1 cross-building move +10 min". Show the before/after total so the improvement is visible rather than asserted.

If — and only if — the team has a Python member with spare hours, an OR-Tools CP-SAT model over the same data makes a strong "advanced" appendix (and justifies the elective C++/GPU mention in the statement). Frame it as a comparison: greedy+local-search vs CP-SAT on the same seed, with solve time and cost. That is a five-minute demo segment with real content, but it is a phase-3 item, never a blocker.

Section 6The AI layer, done safely

6.1 The architectural rule: the model proposes, the database decides

The single most common way a student AI project loses credibility is letting the language model invent facts — a room that does not exist, a slot that is already taken, a capacity it remembers from somewhere. For a system whose entire purpose is correct information, that is fatal. So the boundary is drawn once, in one sentence:

The rule

The LLM never computes availability, never writes to the database, and never produces a number the UI displays as fact. It does exactly two things: it translates messy human language into a structured query (function-calling / tool use), and it renders a result that the deterministic engine produced into a friendly sentence. Everything the AI says about rooms originates from a database row returned by your own code, with provenance attached.

6.3 Model and cost strategy

Use a hosted API with tool calling and a provider-agnostic adapter behind one interface (llm.complete() / llm.tool()). This costs ~40 lines and buys three things that matter on a hackathon timeline: you can switch providers in a minute if a key is rate-limited, the whole app still runs with the AI disabled, and you can state honestly what each call costs.

  • Small, cheap, fast model for intent extraction (structured output) and a slightly larger one only for notice drafting. Cache frequently used prompt prefixes; keep the schema in the system prompt, not in the user turn.
  • Timeout at 8 s and fall back to the deterministic UI with a quiet "smart search unavailable" hint. A judge must never see a spinner of death during a demo.
  • Rate-limit per user (e.g. 20 AI calls/hour) and log every call as an AIInteraction row: prompt hash, tokens, latency, tool args, outcome. This log is both your cost dashboard and your audit trail for the "AI recommended X" question.
  • Prompt-injection hygiene: user text never becomes system instructions; room data is passed as data; the tool layer refuses any argument it would not accept from a form.

8.2 Accountability without a logging graveyard

Requirement 7 says "maintain a history of important bookings and changes to help resolve misunderstandings". Two layers, two different jobs:

Requirement 5 is precise: students may view and may comment or report, but may not modify official bookings. Implement it as three surfaces with hard separation:

1 · View

Today's schedule, week grid, room map, notices feed. Server-rendered, filterable by section, and no mutation routes are reachable from a student session.

A thread attached to a booking. Visible to the booking owner and admins, not to the whole campus. Rate-limited, moderated, editable in the first 15 minutes.

Structured form: wrong room / cancelled but still listed / clashes with another class / outdated / other. Goes to a triage queue with a status lifecycle.

9.3 Notifications: the outbox pattern in one paragraph

Write a Notification row inside the booking transaction, and let a scheduled function send it afterwards. This costs ~20 lines and prevents the classic failure where the mail API times out and the booking is rolled back even though the room is free. It also gives you a retry queue for free: rows with status='pending' older than a minute get retried, and the dispatch log is the proof that notices actually went out.

  1. Request IDs — generate one per request, put it in every log line, return it in every error body. When something goes wrong on stage, you can find it.
  2. Structured logs (JSON) with fields route, actor_id, room_id, duration_ms, outcome.
  3. /api/health returning DB latency, migration version and feature flags — a 2-second judge-pleaser and a genuine readiness signal.
  4. An audit/AI usage panel in the admin UI — recent bookings, rejections, AI calls and their cost. It turns invisible engineering into a visible demo screen.

Schema before screens. Every hour spent on the data model on day 1 saves three on day 6. CREATE TABLE "Room" (
  id            uuid PRIMARY KEY,
  code          text UNIQUE NOT NULL,          -- 'IET20', 'LH08', 'LIB' (campus-spoken, not invented)
  floor_id      uuid NOT NULL REFERENCES "Floor"(id),

  capacity      int  NOT NULL,                 -- normal seating
  exam_capacity int  NOT NULL,                 -- spaced seating (policy, not physics)
  bookable      boolean NOT NULL DEFAULT true,
  accessibility text NOT NULL DEFAULT 'stairs_only',  -- step_free | stairs_only
  zone          text,                          -- IET-FF-NORTH, DB-GF …
  permitted_uses text[] NOT NULL,
  unconfirmed   boolean NOT NULL DEFAULT false -- one of the five source ambiguities
);

CREATE TABLE "Booking" (
  id              uuid PRIMARY KEY,
  ref             text UNIQUE NOT NULL,        -- 'BK-2026-000137'
  room_id         uuid NOT NULL REFERENCES "Room"(id),
  start_at        timestamptz NOT NULL,
  end_at          timestamptz NOT NULL,
  purpose         text NOT NULL,               -- CLASS|EXAM|PRACTICAL|EVENT|SEMINAR|VIVA|OTHER
  headcount       int  NOT NULL,
  section_id      uuid REFERENCES "Section"(id),
  requested_by    uuid NOT NULL REFERENCES "User"(id),
  status          text NOT NULL DEFAULT 'CONFIRMED',
  reason          text,
  is_test         boolean NOT NULL DEFAULT false,
  seed_source     text,                        -- 'demo' | 'user'
  idempotency_key text UNIQUE,
  version         int NOT NULL DEFAULT 0,
  created_at      timestamptz NOT NULL DEFAULT now(),
  CHECK (end_at > start_at)
);
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE "Booking" ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&)
  WHERE (status IN ('CONFIRMED','PENDING_APPROVAL'));

CREATE INDEX ON "Booking" (room_id, start_at DESC);
CREATE INDEX booking_range_gist ON "Booking" USING gist (tstzrange(start_at, end_at, '[)'));
